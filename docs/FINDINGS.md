# Trust assessment

This is a useful historical reconstruction, not an authoritative executable book. On the supplied fixture, 30 of the oracle's 31 two-sided markets match both touch prices exactly as decimal values. All 31 agree within one binary64 ULP of the oracle. BTC_IRT is the exception to literal equality: SQL returns bid `6799828743.5150204` and ask `6800285707.2144403`; the oracle serializes `6799828743.51502` and `6800285707.21444`. Consequently SQL's exact spread is `456963.6994199`, versus oracle `456963.69942`. I retain the event decimals and report this discrepancy rather than rounding the pipeline to fit the key. All 36 reference markets remain visible: 31 two-sided, two bid-only, and three empty. No crossed markets are hidden.

The decisive defect is stale order state. Latest source images can still describe old, active limit orders that the matching engine no longer holds. Correct CDC deduplication alone cannot repair that semantic disagreement. Choosing maximum `__LSN`, then excluding deletes, non-limit modes, closed states, cancellation requests, settled orders, nonpositive remainders and nonpositive prices still crosses all 36 markets. Of 1,580 otherwise-resting orders, 268 (16.96%) have their latest commit before the latest observed source date. At the landed-message level, 537 of 16,308 rows (3.29%) carry a valid JSON commit timestamp on an older day. The reproducible measurement and before/after crossing queries are in `sql/02_queries/02_monitoring/diagnostics.sql`.

My mitigation retains resting candidates only when their latest commit falls on that latest source day in Asia/Tehran. The date is inferred from the stream, so the August fixture can be replayed in October without a hard-coded date or reading the scoring file. It removes all observed crossings and produces the measured touch agreement. This is a heuristic: a real GTC order can legitimately rest overnight without an update, and I will incorrectly exclude it. An obsolete order updated today can survive. A future timestamp outlier can advance the cutoff. At a day boundary, liquidity can collapse in the derived book without any actual cancellation. A global source day can also discard a quiet market when another market advances. These are reasons to withhold an execution guarantee, even with a perfect sample score.

Landing accounts for all 16,308 messages: 16,282 typed rows and 26 dead letters, comprising 19 invalid JSON, six invalid prices, and one invalid side. Error reasons are first-failure classifications; some rows have multiple defects. The typed history contains 224 redeliveries beyond unique `(id, LSN)` pairs. Global latest-state reconciliation prevents their volume from being counted twice. A rejected latest image can still leave an older image visible; rejection capture protects availability, not necessarily correctness. Seven-day histories expire by ingestion time, while a replicated latest-image table retains dormant orders and tombstones. Its distinct-ID cardinality needs an eventual checkpoint-based retirement policy.

I would allow spread, gaps and depth to inform historical liquidity monitoring with crossed, empty-side, source-age and rejection flags attached. I would not let a trader size an executable order from these outputs alone. Depth and fill impact are especially directional: they include bots and all services, omit legitimate older resting orders, and model a static ladder without queue priority, cancellations, fees, latency or subsequent fills. A ten-second snapshot with a thirty-second computation expiry can already be materially stale for trading. `source_as_of` separately exposes that this fixture's source is historical; continuously recomputing it does not make it live.

For accuracy, I would obtain sequence-numbered matching-engine book snapshots and incremental updates, reconcile CDC against them, and require explicit resting membership and terminal lifecycle events. Feed heartbeats, gap detection and replay watermarks should gate publication. Three shards with two replicas protect stored data, but Kafka and the scheduler remain single points of failure, replicas can lag, and chained views plus offset commits are not one transaction. I would add atomic publication of complete snapshot batches and exercise recovery during continuous ingestion. Production-scale performance and bot-at-touch rollups remain the next stage, not claims supported by this small fixture.
